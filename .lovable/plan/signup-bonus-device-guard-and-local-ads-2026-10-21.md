# Signup bonus, device guard and local ads

Your app already has a wallet system that holds real balances and transaction history: wallets, a transaction log, a hashed PIN, and locks that stop anyone changing a balance directly. To keep that data safe, this plan **extends** what's there instead of building a second wallet system.

## What changes

1. **Wallets.** Keep the current wallets table. Add a `device_id` column (optional, unique). The existing hashed PIN stays your `pin_code`. Nothing is renamed or deleted.
2. **One bonus per device.** A new bonus-claims list records each device and each account that got a bonus. Each device and each account can appear only once, so a second claim gets refused.
3. **Signup bonus.** When someone confirms their email, the app reads the device ID sent with their signup. If that device hasn't claimed yet and the overall bonus budget isn't used up, it creates or activates their wallet with a **100 ETB** bonus. The bonus goes in the existing transaction history as a `bonus` entry marked `SIGNUP_BONUS`. If anything fails, signup still works and no bonus is given.
4. **Budget cap.** A settings row stores the total bonus budget and how much has been paid out. Every bonus is checked against it and counted toward it in the same step.
5. **Local ads.** A new ads table: business owner, title, description, image, link, price in ETB, and active on/off. Anyone can see active ads. Owners can create and edit their own ads.
6. **Security rules.** Users can see only their own wallet and transactions. Nobody can change a balance from the app; only the server can. Ads follow the rules in item 5. The bonus-claims list and budget settings are hidden from users.
7. **Signup screen.** The signup form sends the device ID (already generated by the wallet code) along with the account details.

## Technical details
- Migration: `ALTER TABLE wallets ADD COLUMN device_id text UNIQUE` (nullable). Create `signup_bonus_claims(device_id text PK, user_id uuid UNIQUE, amount, claimed_at)` and `bonus_budget(id int PK, cap numeric, spent numeric)`, both RLS-enabled with no client policies and granted to service_role only.
- `handle_signup_bonus()` is a SECURITY DEFINER function wrapped in an exception block. It runs as an `AFTER UPDATE OF email_confirmed_at ON auth.users` trigger, firing when the value changes from null to set. It reads `device_id` from `raw_user_meta_data`, locks the budget row `FOR UPDATE`, upserts the wallet, and inserts a `wallet_transactions` row (type `bonus`, status `completed`, metadata `{kind:'SIGNUP_BONUS'}`, idempotency key `signup_bonus:<uid>`). The existing balance trigger then credits the wallet.
- `local_ads(id, owner_id, title, description, image_url, target_url, price_etb numeric, currency text default 'ETB', is_active bool default true, created_at, updated_at)` with these grants: anon/authenticated SELECT, authenticated INSERT/UPDATE/DELETE. Policies: select where `is_active OR owner_id = auth.uid()`; write where `owner_id = auth.uid()`. Triggers handle `updated_at` and check that the link is http(s).
- Check the existing wallets and wallet_transactions policies: own-row SELECT only, with financial fields still guarded by the existing trigger.
- Signup (`supabaseAuth.ts`) adds `device_id` to `options.data`.
- Tests: on email confirmation the first account on a device gets a 100 ETB bonus; a second account on the same device gets none; no bonus once the budget is used up. Then run the security linter.
